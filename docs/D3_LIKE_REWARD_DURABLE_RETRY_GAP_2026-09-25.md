# D3 遗留缺口：点赞奖励缺少持久化重试补偿

- 记录日期：2026-09-25
- 对应整改项：D3「点赞结算失败的补偿策略」
- 当前状态：**部分完成**。已落地「整事件回滚」与「可见失败提示」，**持久化重试补偿未实现**。
- 阻塞原因：本项需要新增一张数据库表，超出已核准的 D5 单表范围，等待核准。
- 影响面：点赞累计、连续点赞天数，以及由两者派生的两张补签卡。

## 1. 一句话结论

点赞事件写库失败后，这次点赞只留在日志和一条前端提示里，没有任何持久化记录。
一旦 B 站不再推送同一条消息，这次点赞就永久消失：当日累计不补、连续天数不补、本该发出的补签卡也不补。
`like-reward-failed` 事件里的 `retryable: true` 只表示「同一个 msg_id 再来一次会被重新处理」，它不构成「一定会恢复」的承诺。

## 2. 当前处理链路

点赞事件来自直播 WS 推送，入口是 `src-tauri/src/bilibili.rs` 的 `run_bili_live_loop`：
`cmd == "LIVE_OPEN_PLATFORM_LIKE"` → `parse_like_event` → `on_like(ev)` → `handle_incoming_like`。

`handle_incoming_like`（`src-tauri/src/lib.rs`）按以下顺序执行：

1. `reserve_msg_id` 预留去重键，返回 `MsgIdReservation::{NoKey, Reserved, Duplicate}`；`Duplicate` 直接返回。
2. `like_count <= 0` 或 `uid` 为空时释放预留并丢弃。
3. 用 `server_date(timestamp)` 推算点赞日期，缺失时回退本机今天。
4. `state.checkin()` 取打卡管理器；失败则释放预留、发节流提示、返回。
5. `mgr.add_likes(uid, like_count, date)` 在单个 `IMMEDIATE` 事务内完成当日累计、连续天数、发卡与标记写入。
6. 成功则按「先突破 30、后连续 7 天」的顺序播报，并在提交后写历史留档。
7. 失败则记 ERROR、释放预留、发 `like-reward-failed`，返回空。

`add_likes`（`src-tauri/src/checkin.rs`）中「卡数」与「领取标记」总是共同成败，因此不会有「卡已发、标记没写」的重复发卡。
这一步是对的，问题不在这里。

## 3. 缺口本体

### 3.1 三种出口的最终状态

| 出口 | 数据库 | msg_id 缓存 | 前端 | 原始点赞数据 |
|---|---|---|---|---|
| 成功 | 已入账 | 保留 | 正常播报 | 已落盘 |
| 重复消息 | 不动 | 保留 | 无 | 已落盘（首次） |
| 写库失败 | 整事件回滚 | **释放** | 一条失败提示 | **无任何持久化记录** |
| 数据库打不开 | 未触碰 | **释放** | 节流提示 | **无任何持久化记录** |

失败与打不开这两行就是缺口：数据只存在于「内存里那个已经用完的 `i32`」和一行日志文本。

### 3.2 「可重试」成立的前提

释放预留确实让重投能被重新处理。但释放只解决了「重投会被拦掉」这一个问题，它不保证重投一定会发生。
重试的触发权完全在 B 站服务端，本工程既不控制也不知晓。

### 3.3 打不开数据库的路径更彻底

第 4 步失败时连事务都没开始。此时 `like_count` 直接丢弃，同样没有任何记录。
日志只有节流后的不可用告警，无法还原丢了多少次、每次多少赞。

## 4. 为什么不能把可恢复性寄托在服务端重投

- 该 WS 通道是纯推送模型，只有 OP_HEARTBEAT / OP_HEARTBEAT_REPLY 这类控制包，**没有业务消息级 ACK**。
  客户端不回复确认，服务端就没有依据去判断哪条业务消息需要重发。
- 断线重连后是否补发断线期间的点赞包，取决于 B 站服务端实现。本工程既无法控制，也没有可验证的验收手段。
- 点赞事件本身是聚合的，单条 `like_count` 上限为 10000（`MAX_LIKE_COUNT`）。
  也就是说一次丢失可能是一个很大的数字，不是「少 1 个赞」这种可忽略量级。
- 同一 `msg_id` 的重投在正常连接下并非常态。把正确性建立在「说不定会重投」上，等于把数据准确性交给外部不确定性。

## 5. 具体丢失什么

### 5.1 当日累计点赞

`user_daily_likes(uid, like_date, total_likes)`，主键 `(uid, like_date)`。
丢失后该日累计偏低，且不会自我修正。

### 5.2 自然周首破 30 的那张卡

`add_likes` 判定 `total_likes >= 30 && weekly_first_claimed != week_start` 才发卡。
若丢失的那次点赞正是把当日累计从 30 以下推过阈值的那一次，则本周这张卡永久不补。
由于每周只发一次，损失是「整周少一张卡」，不是「少一次计数」。

### 5.3 连续点赞天数，以及连带的断链

`user_like_streaks(uid, current_streak, last_like_date, streak_reward_issued)` 是按增量维护的：

- `date == last_like_date + 1` → `current_streak += 1`
- `date != last_like_date` 且不连续 → `current_streak = 1`
- 无记录 → `current_streak = 1`

所以丢一天不只是少一天。假设第 1–4 天已入账，第 5 天丢失，第 6 天正常到达：
第 6 天看到 `last_like_date = 4`，既不等于 6 也不等于 4+1，于是 `current_streak` 被重置为 1。
**已经攒下的 4 天进度一起清零。**

如果丢失的正好是第 7 天（发卡日），代价是：重置连击 + 少一张补签卡 + 只差一步的前 6 天全部作废。
严重度明显高于「少记几个赞」。

## 6. 与补签失败的对比：为什么补签不需要同样的机制

补签是主播手动发弹幕触发的。失败时 `execute_retroactive_checkin` 返回「补签失败，请稍后再试」的回复文案，
主播看到后可以再发一次，损失是可人工恢复的。

点赞没有这条路径。它不是人触发的，主播既不知道丢了哪一次，也无法手工补发一条点赞事件。
这正是同一类「事务失败」在两条链路上严重度不同的原因。

## 7. 现有缓解措施及其边界

| 措施 | 覆盖 | 边界 |
|---|---|---|
| 整事件回滚 | 不产生半截数据 | 不解决数据丢失 |
| 释放 msg_id 预留 | 重投不会被误判为重复 | 不产生重投 |
| `like-reward-failed` 事件 | 主播当场知道并去查库 | 提示关掉就没了，无累计账目 |
| ERROR 日志 | 事后可检索到失败次数 | 无法区分「已由重投补回」与「真的丢了」 |
| WS 包类型计数摘要 | 能看出「收到过点赞包」 | 只统计收到，不统计入账成功数 |

结论：当前只有「可观测」，没有「可恢复」。
特别地，由于没有入账成功计数，运维无法用「收到包数 − 入账数」算出丢失量。

## 8. 修复方案候选

### 方案 A（推荐）：意图账本表 + 同事务销账 + 重放前按日期重算

三张表之外新增一张意图账本，记录「这次点赞打算入账但还没成功」。
关键点是销账必须与应用入账放在同一个事务里，否则崩溃窗口会造成重复计数。

写入顺序：

1. 事务 T1：`INSERT INTO pending_like_rewards(...)`，单独提交。这是持久化的意图。
2. 事务 T2（`IMMEDIATE`）：执行入账累加 **并** `DELETE FROM pending_like_rewards WHERE id = ?`，一起提交。
3. 启动时与运行期定时扫描剩余行，对每行重跑第 2 步。

崩溃窗口分析：

- T1 与 T2 之间崩溃 → 账本有行、入账未发生 → 重放正确。
- T2 提交成功 → 入账与销账同时持久化 → 不会重放，不重复计数。
- T2 失败或回滚 → 入账与销账一起回滚 → 账本仍有行 → 下次重放。
- T1 自身失败 → 没有任何持久化可能，此时数据库整体不可写，任何方案都救不了，属于必须接受的边界。

**但只加账本还不够。** `current_streak` 是增量维护的，重放历史日期会算错：

第 5 天丢失、第 6 天已入账（`last_like_date = 6`，`current_streak = 1`），
再重放第 5 天时 `date = 5 != 6` 且不等于 `6 + 1`，于是 `current_streak` 被再次重置为 1、`last_like_date` 倒退成 5。
数据从此处在「已记录第 6 天、但游标停在第 5 天」的矛盾状态。

因此方案 A 必须同时包含第二步改造，二选一：

- A-1：入账时不再增量维护连击，改为按 `user_daily_likes` 中该用户的点赞日期集合倒推连续天数。
  这与打卡侧 `internal_calc_continuous` 的倒推思路一致，天然与重放顺序无关。
  代价是改变了原工程「点赞增量维护连击」的算法，需要确认这种偏离是否可接受。
- A-2：重放前检查是否已有更新的点赞记录。仅当待补记录的日期晚于当前 `last_like_date` 时补记；
  乱序则保留记录、告警、不臆改连击。实现小，但只能救「失败后没有更新点赞」的那部分场景。
  崩溃很久后重启的情形基本都会命中乱序，覆盖率差。

### 方案 A′（精简）：账本 + 同事务销账 + 只补记顺序安全的记录

即方案 A 的落库部分加上 A-2 的判据，不做连击算法改造。
适合「先拿到大部分收益、把算法改造留作后续」的节奏。

### 方案 B：数据库外的追加流水文件

把待处理点赞写进独立追加文件，成功后追加一条销账记录，启动时重放。
好处是完全不动数据库结构，不需要新表核准。
代价是引入第二套持久化：文件与数据库之间没有事务，崩溃后要靠重放去重；
还要自己处理截断、损坏、磁盘满；并且同样的重放乱序问题依然存在。
在已经有 SQLite 的前提下，这比新增一张表更复杂，不推荐。

### 方案 C：仅在进程内重试

失败后把事件放进内存重试队列，定时重试若干次。
实现最省，能覆盖「数据库瞬时锁冲突」这类短暂故障。
不覆盖进程退出、崩溃、重启，也不覆盖数据库长时间不可用。可作为方案 A 的补充，不能替代。

### 方案 D：不修，只补齐可观测

保留当前行为，把「失败次数、丢失点赞总数」落成持久化统计并向主播展示。
明确把它定义为产品取舍：单次点赞丢失不追补。
如果选这条路，第 5.1–5.3 节的后果需要被显式接受，尤其是连击清零。

### 对比

| 方案 | 新增表 | 崩溃后可恢复 | 乱序正确性 | 实现量 | 残留风险 |
|---|---|---|---|---|---|
| A | 1 张 | 是 | 正确（A-1） | 大 | 连击算法偏离原工程 |
| A′ | 1 张 | 是 | 仅顺序安全场景 | 中 | 乱序场景丢弃并告警 |
| B | 0 张 | 是 | 同 A 问题 | 中大 | 两套持久化不一致 |
| C | 0 张 | 否 | 不涉及 | 小 | 重启即丢 |
| D | 0 张 | 否 | 不涉及 | 小 | 全部后果照单接受 |

## 9. 推荐方案 A 的落地设计草案

### 9.1 表结构

```sql
CREATE TABLE IF NOT EXISTS pending_like_rewards (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    uid TEXT NOT NULL,
    msg_id TEXT,
    like_date INTEGER NOT NULL,
    like_count INTEGER NOT NULL,
    created_at INTEGER NOT NULL,
    retry_count INTEGER NOT NULL DEFAULT 0,
    last_error TEXT
);

CREATE UNIQUE INDEX IF NOT EXISTS idx_pending_like_msg_id
    ON pending_like_rewards(uid, msg_id)
    WHERE msg_id IS NOT NULL AND msg_id <> '';
```

设计说明：

- `msg_id` 允许为空。空 `msg_id` 的事件本来就不参与去重（`MsgIdReservation::NoKey`），
  用一个条件唯一索引只对非空值去重，与现状语义一致，也不会用「文案 + 时间」伪造键。
- 主键用自增 `id` 而不是 `(uid, msg_id)`，就是为了让空 `msg_id` 的行能共存。
- `retry_count` 与 `last_error` 用于重试上限判定与排障，`last_error` 只存错误分类，不存昵称。

### 9.2 重试触发时机

- 打卡子系统打开成功后立即扫一次（覆盖「上次运行期间失败 + 本次启动」）。
- 运行期定时，间隔建议 60 秒；数据库刚从不可用恢复时额外触发一次。
- 重试本身仍用 `IMMEDIATE` 事务，与正常入账共用同一段逻辑，避免两份实现漂移。

### 9.3 重试上限与放弃策略

- 达到上限（例如 20 次）或跨周后仍失败：**保留记录不删除**，记 ERROR，并只提示一次。
- 不静默删除。删除等于丢失不可追溯，与「持久化意图」的目的相反。

### 9.4 需要产品确认的行为

- 补记昨天的点赞会按昨天的日期计算周起始，**可能追发上一自然周的卡**。
  这符合「按事件发生日结算」的口径，但表现为「本周突然多一张卡」，需要确认是否接受。
- 补记会连带修正连续天数。如果采 A-1，连击会按日期集合重算，可能出现「补记后连击变长、随即发卡」。

## 10. 需要先决策的点

1. 是否核准新增第二张 V2 专用表 `pending_like_rewards`。当前只核准过 `processed_retro_commands` 一张。
2. 选 A-1（改造连击为按日期倒推）还是 A-2（仅顺序安全场景补记）。
   A-1 会让点赞连击的实现偏离原工程算法，需要原工程一致性上的确认。
3. 重试上限取值，以及超限后是保留告警还是向主播弹出确认。
4. 是否同时补一个「入账成功计数」，让「收到包数 − 入账数」可算，补齐第 7 节的观测缺口。

## 11. 验收方式

实现后至少覆盖下列用例，测试沿用现有的故障注入手法
（在 `checkin.rs` 内用 `inject_sql_for_test` 挂 `RAISE(ABORT)` 触发器制造失败）：

| 用例 | 断言 |
|---|---|
| 入账失败后账本留行 | `pending_like_rewards` 恰好一行，字段与事件一致 |
| 重放成功后账本清空 | 该行被删除，且 `user_daily_likes` 只加了一次 |
| 重放两次不重复计数 | 第二次重放无行可处理，累计值不变 |
| T2 提交成功不重放 | 模拟重启后扫描，无待处理行 |
| 乱序重放 | 按所选分支：A-1 连击按日期正确重算；A-2 不修改连击且留下告警 |
| 空 `msg_id` | 不写唯一索引冲突，两次空 `msg_id` 事件可各自留行 |
| 打不开数据库 | 不 panic，恢复后待处理事件可被补记（若一并修第 3.3 节） |
| 重试上限 | 达上限后记录保留、不删除、只提示一次 |
| 迁移 | 老库打开后仅新增该表，原五张表结构逐字不变 |

## 12. 实施时会牵动的既有约束

- **迁移测试口径。** `test_open_legacy_captain_profiles_db`（`src-tauri/src/checkin.rs`）
  断言 `after.len() == before_schema.len() + 1`，并校验新增表名必须是 `processed_retro_commands`。
  加第二张表后这两处都要改，且要改成「按表名白名单」而不是按数量。
- **一个已存在的隐患。** `test_real_repo_legacy_db_copy_compatible`（同文件）断言
  `before_schema.len() == after_schema.len()`（"迁移不得增删表"）。
  但 `init_schema` 现在总会创建 `processed_retro_commands`，所以一旦仓库里放入真实的
  `MonsterOrderWilds_configs/captain_profiles.db`，这个断言必然失败；
  它目前只是因为没有该文件而在第一行 SKIP，属于「靠跳过保持绿色」。
  本项改动会碰到同一处，建议顺手把它改成与上一个测试一致的白名单口径。
- **Lite 形态。** 点赞与打卡在 Lite 下停用（`handle_incoming_like` 首部 `IS_LITE` 直接返回），
  本项不影响 Lite，但新增表会出现在 Lite 构建能打开的同一个库文件里，需确认无副作用。
- **原工程一致性。** 新增表是 V2 相对原 C++ 工程的第二处结构偏离，A-1 还会带来算法层面的偏离。
  两处都需要显式确认。
- **编码与测试规则。** 新增文件按 UTF-8 with BOM；新增业务逻辑必须配套单测并立即 `cargo test`；
  不自动提交，改动留工作区供复查。
