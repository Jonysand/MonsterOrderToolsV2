# 核心点怪、打卡补签与日志的代码级修复方案

> 方案日期：2026-09-25；设计基线：`cb0e2c56418b5f12228ea4922de5759900db5ee2`。问题证据、严重度及未验项在 `docs/CORE_FLOW_REVIEW_2026-09-25.md`。**本文件是实施方案，不代表代码、测试或发布包已经修改。**
> 旧工程对照使用公开仓库 `Jonysand/MonsterOrderTools` 提交 `40bca8c9af3ad68c1f8c4acd77c96ac725c826be`。本文明确区分旧行为、V2 的有意差异及尚待产品确认之处。

## 1. 目标、约束和工程原理

**成功条件：**一次前端拖拽不能删掉另一路新订单；正常持久化失败必须可见并可重试；打卡／卡片的回执只在事务提交后产生；Lite 启动不得碰打卡库；完整版即使关闭语音也保留旧版规定的 History；凭据状态、下一次开播用的凭据和磁盘文件一致。每项修复均有故障反测，不以“旧单测仍绿”代替。

```text
    B站包 → parser → 业务管道 → ┬→ QueueManager(队列 Mutex + revision) → 单写盘锁 → order_list.json
                             ├→ CheckinManager(连接 Mutex + SQLite 事务) → captain_profiles.db
                             ├→ TTSManager(可选语音队列)
                             └→ 事件产生处 → History；状态/错误 → 安全诊断 Logs
    MainWindow / OverlayWindow → IPC + 预期 revision → 后端核对 → 权威版本快照事件
    凭据文件 → 验签 → 原子替换 → 内存凭据快照 → 下一次 B站会话
```

- **队列不变量：**凡用客户端**整队快照**改写顺序或状态的命令只能提交条目 ID 的顺序，并必须核对 expected revision；按独立用户 ID 的新增／完成在后端当前状态上操作、带回权威新快照，不因另一个用户入队而被无谓拒绝。磁盘单写者保证快照按序落盘，写失败保留脏位；撤销还须核对旧 item 的身份，不能用旧订单覆盖同 UID 新单。
- **数据库不变量：**同一次打卡／点赞领奖／批量补签中的所有相关 SQL 要么全部提交，要么全部回滚；内存库只能用于显式注入的测试，不得成为生产静默兜底。
- **名单不变量：**读旧名单→计算新名单→落盘→提交内存必须在一次串行编辑中；读旧 revision 的前端整表更新不得覆盖后端新状态。
- **Lite 不变量：**仍可用点怪、字典／禁点名单、B站长连和 Logs；不创建、打开、迁移 `checkin.db` 或 `captain_profiles.db`，也不产生业务 History/TTS。
- **安全目标与现状：**真实 `credentials.dat` 的 Base64＋`@MonsterOrderSecret@`＋HMAC-SHA256 格式不改；Windows `IdCode` 仍只在 `HKCU\Software\MonsterOrderWilds\IdCode`。**普通 Logs 不记录密钥、弹幕正文或个人档案是待实现的目标，不是当前保证**：现有点怪 INFO 含昵称、TTS 队满 WARN 含文本、若干外部错误还可能含原始响应；F3 必须全量盘点后才可宣称达标。History 的业务原文另按原产品用途管理。

### 1.1 明确的方案取舍

| 争点 | 选用方案 | 不选的方案与理由 |
|---|---|---|
| 排队拖拽 | 后端 `revision`＋严格全排列校验；在锁内只搬移后端现有条目 | 只在前端比较长度／成员有 TOCTOU；只检成员也会覆写优先位与图标 |
| 队列写盘 | 独立 `queue_flush_lock` 串行后台和命令落盘；业务 `queue_mutex` 仅短暂取快照 | 全程持队列锁写磁盘会阻塞弹幕；仅延长 500ms 节流不能防倒写 |
| 数据库不可用 | 完整版显式**停用打卡子系统并展示不可持久化错误**，核心排队继续；Lite 完全不实例化 | 整个主程序退出会阻断点怪；无提示切内存库制造资产丢失 |
| 凭据轮换 | 拒绝在旧会话仍活动／尚未停止时导入；等待安全断开后导入并立即用于**下一次**连接 | 在运行中的旧长连上直接替换 `Arc` 无效；未经编排停止／重启可能同时运行两场 |
| 两个 DB 文件并存 | **先显著提示冲突、保持当前旧库优先规则作为兼容过渡；记录既有活动库来源**，待用户确认离线合并／切换 | 无提示挑选会使另一份资产隐身；直接停用所有打卡会让已有双库用户失去现有可用性；直接复制 `.db` 可漏 WAL |
| History 来源 | 在各业务事件**形成文本时**恰好记录一次，TTS 只负责播报 | 在 TTS 出队处统一写会受语音开关／队满影响，且无法忠实记录查询和进场 |
| 补签重复投递 | **安全增强批次一并落实**：`msg_id` 与扣卡放同一 SQLite 事务去重，列为发布门禁 | 入口直接预占现有 DM 缓存会误判首次点怪；只靠内存缓存不能覆盖重启重投 |

无 CPU、锁等待、磁盘延迟或 500 条弹幕的 profiling 数据；本方案**不提供臆造的耗时或提速比例**。实施后的性能门禁在第 9 节列出采集方法。

## 2. 阶段 A：先封住直播订单丢失（Q01、Q02、Q08、Q10）

### A1. 后端只接受“版本＋用户 ID 顺序”

**修改位置：**`src-tauri/src/queue.rs` 的 `QueueManager` 及各变更方法，`src-tauri/src/lib.rs` 的 `get_queue`、`reorder_queue`、队列增删恢复命令及 `queue-updated` 发送点；`src/types.ts`、`src/views/MainWindow.tsx`、`src/views/OverlayWindow.tsx`。

1. `QueueManager` 新增只在内存中的 `revision: u64`。**每次确实改变条目集合、顺序或任一条目字段**都递增：新增、完成、清空非空队列、提权、恢复、重排、以及 `add_or_update` 里已有用户的怪名／历战等级／图标／舰长等级变化，虽然后者返回 false 仍须递增。未命中删除与重复提权不递增。`load_from_file` 初始化 revision 为 0；磁盘 `order_list.json` **保持现有 JSON 数组**，不混入协议字段。
2. IPC 返回／事件改用统一快照 `{ items: QueueItem[], revision: number, persistence: "Saved" | "PendingRetry" }`。`persistence` 表示**最近一次有序内存版本是否已确认落盘**，磁盘失败和写入中的状态均为 `PendingRetry`，可另附不含用户数据的失败分类／次数；它不是永不失败的承诺。`get_queue`、`add_order`、`dequeue_by_user_id`、`restore_order`、`reorder_queue` 等命令返回和 `queue-updated` 都须使用它；`clear_queue` 同样返回快照或成功后主动获取。`flush_queue` 改为返回保存结果，失败保留 `dirty`，命令回传 PendingRetry 并向主／悬窗 emit `queue-persistence-changed`，下一 tick 成功后事件改为 Saved；冷启动 `get_queue` 可重取权威状态。不得继续无版本无保存状态地 `setQueue([])`。在队列锁内同时捕获 items、revision 和保存状态；锁外即使事件乱序到达，前端也只应用不小于当前已知 revision 的权威快照。**同 revision 的持久化状态可从 PendingRetry 更新为 Saved，但迟到的 PendingRetry 不能盖回 Saved。**
3. `reorder_queue` 入参改为 `ordered_user_ids` 和 `expected_revision`。**同一队列锁内**先比版本，再检查无重复 ID、恰好覆盖当前每位用户；不符返回明确“队列已变化，请刷新后重排”，不触碰内存／磁盘。按 ID 从后端当前条目重组列表，保留它们的真实 `id`、`is_priority`、`timestamp`、`icon_url` 等字段。后端不再信任客户端发来的 `QueueItem[]`。
4. 主窗口拖拽从起始 index 改为记 `user_id` 和起始 revision；结束时按 ID 算顺序。悬浮窗 `authoritativeRef` 仅作预览，不得先用乐观顺序冒充新的权威 revision。命令成功应用返回快照；冲突时取最新快照、提示重拖。**所有**轮询、事件与 IPC 成功回调都走一个版本检查函数，避免旧命令返回裸数组绕过保护。
5. 对相同队列的连续拖拽，若原顺序未变化就不写盘；不要把旧版的优先排序规则随本项一并改写。手动顺序遇后续新增被全排序覆盖属第 8 节待确认业务决策。

**反测／验收：**初始 `[A,B]`、先加 C 再提交旧版 `[B,A]`，必须拒绝且 C 留在队列和 `user_index`；同成员但 A 刚提权，旧重排也拒绝；已有用户通过 `add_or_update` 改怪名／等级或图标时，revision 虽返回 `added=false` 仍递增，迟到的同版本旧事件不能覆盖它；ID 缺失、重复和空数组覆盖非空队列均拒绝；完成后旧事件／旧 `get_queue` 应答不得让 UI 倒退。现有 `queue::test_manual_reorder_queue` 需从整对象改测 ID＋revision；前端对主窗下标漂移补交互回归。完整版和 Lite 同测。

### A2. 队列磁盘只允许一个写者；成功后才清脏

**修改位置：**`lib.rs::AppState`、`flush_queue`、`save_queue_now`、`shutdown_app`；`queue.rs::write_json`。所有调用者均先放开 queue mutex 再请求刷盘。

1. 增加由克隆的 `AppState` 共享的 `Arc<Mutex<()>> queue_flush_lock`。后台 500ms 任务与手动命令都必须按**`flush_lock → queue_mutex`**的顺序取锁；写锁涵盖取 `{json, revision}`、临时文件写入、替换目标文件、更新脏标记。禁止持 `queue_mutex` 再进入刷盘，否则可能死锁。
2. 获得写锁后，短暂持队列锁取快照和 revision，再放锁写盘；完成后重拿队列锁：**仅当最新 revision 等于已保存 revision 时清 `dirty`**。写盘期间若来了新弹幕，新 revision 保持 dirty，由下一 tick 继续保存；**任何写入尝试失败都要把 dirty 设置为 true 并记 WARN／PendingRetry，即使它是原先 `dirty=false` 的 force 保存**，随后 500ms tick 再试。对于空队列重复 clear、未命中的 dequeue 等实际无变更情况，也可在入口不强制写盘以减少无效故障。不要在异常时删旧目标文件。
3. `queue.rs::write_json` 使用**目标同目录的唯一临时文件**（`create_new`，进程 ID＋递增序号），`write_all`／`sync_all` 后再 `fs::rename(tmp, target)`；失败清除本次临时文件，不先删目标，不把半写内容当权威。Rust [`std::fs::rename`](https://doc.rust-lang.org/std/fs/fn.rename.html) 明确会尝试替换已存在的普通文件；**“Windows 只要目标存在就不能 rename”是误报**。独占占用或权限错误仍可能使替换失败，应保留旧目标并重试。不承诺在所有断电情形下达到硬件级持久化。
4. 手动命令在“内存已变、写盘失败”时，不能只返回通用错误让前端以为动作没发生并重发；结果或状态须明确标出“内存已更新，磁盘待重试”，前端刷新权威快照并警告。退出强制保存若失败亦记录具体错误。
5. 当前 `flush_queue` 在 `cfg!(test)` 下直接跳过：将真实保存逻辑抽成**注入测试路径／writer**的私有函数，生产包装仍用规范目录。测试绝不借 `paths::config_dir()` 写用户真实队列。

**反测／验收：**可控屏障让后台在持 `queue_flush_lock` 时停在旧快照写盘前；此时更新内存队列并启动强制保存，确认强制保存**等待写锁**；释放后台后，后台旧快照先落盘、强制保存再写最新队列，最终磁盘为新队列。不能要求强制保存先于后台继续完成，否则测试本身会死锁。注入一次写失败后 `dirty=true`，再运行一次 tick 则文件恢复且清脏。旧快照落盘期间新弹幕入队不得清掉新 revision 脏位。Windows 临时目录测试目标已存在可被替换、目标占用时旧文件仍可读且错误可重试。原 500ms 节流与锁外磁盘 I/O 保留。

### A3. 撤销完成和拖错条目的补丁

`lib.rs::restore_order` 必须检查 `queue.rs::restore` 的 bool。若同一用户已重排新单，返回明确冲突，不强制落盘／不发“成功”事件；悬浮窗 `handleUndo` **在后端确认后**才弹出撤销栈顶，失败保留条目、提示并重新获取队列。主窗口第393—418行拖拽记录 UID 而非下标。验收：完成 A→A 又点新单→撤销旧 A，保留新单并显示失败；拖 B 时优先单 P 插队，不能实际搬动 A。此补丁不要绕过 A1 的后端 revision 保护。

## 3. 阶段 B：怪物编辑、手动点单与禁点名单（Q03—Q07、Q09）

### B1. 在权威字典上拒绝同名和撞名

**修改：**`lib.rs::save_monster_entry` 的 `edit_and_save` 闭包、`monster.rs::MonsterDataManager::edit_and_save`、`MonsterListTab::saveDraft`。在任何 `raw.remove/insert` **之前**检查：`original=None` 且目标名已存在→拒绝；`Some(old)` 但旧名不存在→拒绝；`old != name` 且目标名已存在→拒绝；原名不变的正常编辑允许。返回明确错误，不能覆盖图标、别称或名册。前端改原名时复用已有 `askConfirm` 二次确认；前端预检查仅供提示，后端是最后一道校验。

字典编辑为低频操作：在 `MonsterDataManager` 加单一编辑互斥锁覆盖**读当前文件、校验、修改、写盘、热重载提交**；匹配热路径继续短暂读 `RwLock`。避免两个编辑基于旧文件各自写回。**字典改名后** `roster.rename_item`、**字典删除后** `roster.remove` 若落盘失败，当前两条代码均只记 WARN 却向前端报成功；应返回带“词库已修改、名单未同步”提示的部分完成状态，立即重取两份权威视图并提示修复，不宣称两个 JSON 文件有跨文件原子事务。是否进一步实现跨文件恢复协议，按故障频率再议，不在本轮臆造通用配置事务框架。

**反测：**用临时词库副本做“新增黑龙”“黑龙改名碰雌火龙”“编辑时旧名已被删除”，均拒绝且文件字节、别名命中与内存状态不变；两个编辑依次改不同条目均保留。另在词库改名／删除成功后，让对应名单 `rename_item`／`remove` 写入失败，UI 不得谎报“全部保存成功”，须看到部分成功告警及刷新后的两份真实快照。不可对项目真实 `monster_list.json` 做破坏性测试。

### B2. 主播面板按**原名精确取键**，后端检查名单

`monster.rs` 为**选怪面板**增加只查 `inner.monsters` 的精确原名读取；面板调用后端新 `add_picked_order` 或为现有 `add_order` 增加明确来源参数，由后端对“面板选中”的原名执行精确查键和禁点验证，不能重新跑弹幕别名匹配。按所选原名取默认历战等级／图标，`tempered_level=None` 保留“按默认值”，`Some(0/1/2)` 保留主播显式覆盖；入队前由后端检查 `state.roster.is_blocked(原名)`，禁点即拒绝。Toast 用后端实际确认的条目，不直接拿未校验的请求文案。**兼容性边界：**当前通用 `add_order` 在未知怪物未命中时允许按原文入队（`lib.rs` 第223—231行）；该路径是否继续开放、改为受控的手动自由输入、或全面拒绝，属于产品决定，不能把“拒绝未知名”伪装成修错怪的必要变更。未确认前保留旧契约，仅在面板原名入口要求字典内精确命中。

若要求禁点编辑与入队严格线性一致，在维持当前 **`queue_mutex → monster read → roster read`** 的锁序下，名单只读 guard 应持续覆盖“检查→入队”；名单写入不得反向先拿 roster 写锁再拿 queue 锁。字典在精确查询后被删除的旧排队项是否回溯由既有规格决定，不擅自扩展为全局写锁。

**反测：**把“黑龙”作为别的怪的自定义别名，面板仍精确点中原名黑龙；选禁点原名必须拒绝；相同情形下弹幕点怪仍按旧别名匹配和禁点逻辑。原有 `add_order` 的未知名字兼容用例在产品决策前须保持；若选新 `add_picked_order`，仅面板入口应拒绝未知名字。Lite 与完整版同测。

### B3. 草稿冲突和选怪筛选不允许误导

`MonsterListTab.tsx::draftConflicts` 不得再以**保存前** `conflicts.has(w)` 作为门槛；对草稿每个原名／别称查 `owners.get(w)`，剔除旧 `draft.original`，只要有其他拥有者就展示冲突。胜出者由“**新草稿原名＋其他拥有者**”重算，与当前后端按名称排序的规则一致，不能在改名时继续用旧名算赢家。别称冲突按当前规格警告，不一律禁用保存；**原名撞名**必须由 B1 拒绝。

`MonsterPickerPanel.tsx` 的 `selectedEntry` 只能来自当前 `hits` 且未被禁点；当搜索、作品或名单变动使已选条目失效时**清空选中**，不要静默改成第一只。提交前同步再验一次（防 `useEffect` 尚未运行）。补前端模拟／组件交互测试：原名不在筛选后不能提交；已选怪被禁点不会自动点另一只；把已有单一归属别称给新条目应即时提示。

### B4. 名单后端低频编辑串行化＋前端版本校验

**生产可达性先说明：**`MonsterRoster::commit` 在 `roster.rs` 第145—148行未持写锁先写盘、后提交内存，两个**直接调用公有 API 的 Rust 线程**可让磁盘为乙、内存为甲；但本版 `set_monster_roster`／字典编辑均为 Tauri 默认**主线程同步命令**，[Tauri 调用说明](https://v2.tauri.app/develop/calling-rust/#async-commands) 不保证此后端两线程交错能由当前普通 UI 直接触发。**前端陈旧整表请求无 CAS**是另一个风险，即使后端顺序执行也应防御。验收分别测试，不混成一个“UI 必现”结论。

- `roster.rs` 保留盘上 `{ "items": [...] }`。用单一低频编辑锁串行**取旧快照、计算目标、`write_atomic` 成功、赋内存／递增 revision**，失败时内存仍旧；`add_all/remove/rename_item/replace/clear/save` 统一经过它。正常弹幕仍短读名单。别名词库写锁和队列锁的顺序不得相互反转。名单写盘在同目录建唯一临时文件，避免多个直接线程调用共用 `.tmp`。
- 对 IPC 另提供 `{data:{items:[...]}, revision}` 的快照，`set_monster_roster(data, expected_revision)` 在编辑锁内做 CAS。版本不符不写盘，错误提示“名单已变化，请刷新”。导入合并在冲突后可重新读取、按“追加新的条目”重算；**导入覆盖**若名单中途变化必须重新确认，不能偷偷重试覆盖。
- `MainWindow::commitRoster` 的 300ms 防抖仍可保留，已发 IPC 不能用 `clearTimeout` 撤销；只准一个 in-flight 提交，成功后用返回版本提交“用户期间又修改”的最新意图。旧请求失败不无条件 `rosterRef.current=prev`，应获取后端权威快照；`handleImportRoster` 等真正保存成功后才显示“导入完成”。名单 JSON 导入／导出继续使用既有格式，不把 revision 写进用户文件。

**反测：**隔离目录屏障安排 A、B 两个 Rust 线程同时 `replace/add_all`，修后盘与内存相同，`add_all(甲)` 与 `add_all(乙)` 均保留；两个 IPC 以同一旧 revision 提交，不允许后到的旧请求抹去新名单；重点模拟前端持有旧名单→后端 `save_monster_entry` 改名或 `delete_monster_entry` 清理名单→旧前端调用 `set_monster_roster`，后端必须拒绝旧 revision。再用可控 Promise 模拟旧保存失败、新保存成功，前端不得恢复旧画面。当前原生文件选择／确认是同步命令，不能把“弹窗中一定插得进第二个后端命令”作为稳定重现条件；测试直接控制后端顺序和旧快照。不要用“Windows 存在目标文件时 rename 必失败”作测试前提。

## 4. 阶段 C：打卡数据库的真实持久化与 Lite 隔离（D01、D06、M01）

### C1. 不可用时显式停用打卡，核心排队照常

改 `lib.rs::AppState` 初始化路径，不再使用 `CheckinManager::new(None).unwrap_or_else(new_in_memory)`。**选用** `checkin_mgr: Option<Arc<CheckinManager>>` 加只读、脱敏的初始化错误状态，而非数据库故障就终止全部程序：完整版建库成功→Some；失败→None＋`log_error!`＋可查询的 `get_checkin_status`；打卡／补签／点赞／GM 入口遇 None 均拒绝写入，**不能**把内存实例给生产业务。现有 `AppState::new_test` 仍可显式注入内存库。

事件管道必须有反馈：`handle_incoming_danmu` 返回的是 `DanmuProcessResult`，不是 `Result`；有权限用户发打卡／补签／查询而 DB 为 None 时，后端应 emit 一次专门的 `checkin-unavailable` 载荷（只含非敏感原因码和提示文本）、记录有节流的 ERROR、提前 return，**不能**落入普通 TTS 朗读或伪造成功气泡；`OverlayWindow.tsx` 订阅该事件展示“打卡数据不可持久化，请检查本机数据库”。非业务指令仍按点怪主流程继续。点赞 `handle_incoming_like` 只有 `Vec<String>` 返回值且无前端失败回执，应 emit 同一类不可用事件（对高频 LIKE 提示按时间节流、主窗口常驻状态不节流），不得悄悄丢掉。GM 命令本来返回 `Result`，在入口 `ensure_not_lite` 后继续明确 `Err`；主窗口 `get_checkin_status` 冷启动读取并持续展示可用／停用／故障。

Lite 下直接置 None，**在路径检测、`create_dir_all`、`Connection::open`、初始化 schema 之前**短路，并跳过 `CheckinLearner::from_resources`、打卡相关后台任务；`paths.rs::ensure_seeded` 第126—168行 Lite 当前仍复制本地语音 zip、分词词典与 `voices/`，须按 `IS_LITE` 分支仅播种点怪核心资源；`lib.rs` 第1970—1977行当前无条件清理 `TempAudio`，Lite 下也要跳过 `tts::cleanup_old_cache`，避免删除与完整版共用数据目录中的音频留档。别误伤点怪和 B 站连接。`src-tauri/src/checkin.rs::init_schema/migrate_schema` 的建表＋缺列升级宜置于一次事务，避免半迁移。前端冷启动应通过 `get_checkin_status` 获取可持久化状态快照，不能仅依赖 setup 阶段可能丢的单次事件。Lite 的状态显示“按构建形态已停用”，而非“数据库故障”。

**反测：**将完整构建的 DB 路径设成临时只读目录／损坏文件，程序仍能点怪，但打卡、点赞、补签、GM 全部返回明确错误，主窗口冷启动显示不可持久化状态；有权限用户发送指令不会生成成功气泡，也不会掉入普通朗读，悬浮窗能看到不可用提示；连续高频 LIKE 只弹节流提示且不写库，重启不出现看似成功的资产。Lite 用临时缺列旧库及 TempAudio 过期目录启动后，校验数据库主文件、schema、sidecar 和历史语音目录都不被程序打开／修改／清理。开发测试不要指向 `D:\publish_v2`。

### C2. 固定库来源，拒绝双文件静默切换

将 `checkin.rs::get_default_db_path` 的“旧库存在就选旧库”改为目录内可单测的解析器／显式活动库状态：仅 `captain_profiles.db` 存在→沿用旧库；仅 `checkin.db` 存在→沿用既有 V2 库；均不存在→新建 `captain_profiles.db`，避免未来继续裂库；两者同时存在→**当前交付阶段保留既有 `captain_profiles.db` 优先规则，弹持久化的高可见警告，列出两份文件路径与活动库名，不自动合并或删除，给用户离线恢复／备份步骤**。首次从 `checkin.db` 切到新增旧库时不能把旧 V2 数据“失踪”伪装成正常：如已有活动库标记且路径仍有效，保持标记指向的库、发冲突警告，等待用户选择；旧安装**在升级后首次启动时就同时见到两个库**而没有活动库标记，则无法从文件名判断哪份才是此前活动库，本阶段继续旧库优先，但必须显示另一份 V2 数据处于**未展示、并未删除**的状态，禁止自动清理旧文件，并提供退出应用、备份两套库、由用户选择／离线合并后再恢复的步骤。此边界**只修复静默性，不保证无标记双库时资产自动重新可见**，需要用户确认是否宁可停用打卡直至人工处理；不能把“已告警”写成“数据已经合并”。活动库标记必须原子保存，标记指向的文件缺失应报告错误而非悄悄改库。是否把双库状态升级为“停止打卡直到离线合并”或自动迁移，需要先统计既有用户分布、确认同 UID 明细／卡片冲突规则并征得用户决策。禁止自动累加同一 UID 的卡数或只复制 `.db`；WAL 可能还有未 checkpoint 的行。离线合并应另开迁移工单，用 SQLite backup API 在用户授权的隔离数据副本上完成一致性备份和冲突验收。

**反测：**四种文件组合测试路径与状态；有活动库标记的 `checkin.db` 用户在后来出现旧库时仍读原卡数并得到双库警告；升级后第一次就双库且无标记的用户保留当前旧库优先，必须显示“另一份 V2 数据未展示、未删除”的持久警告及离线恢复步骤，不能声称两份资产已合并；标记指向文件被移走时不静默切换；两原件哈希／mtime 保持不变，无擅自合并。旧五表仍允许现有的 `cumulative_days`／`weekly_first_claimed` 缺列迁移，非目标字段与历史记录保持；另新增一张 V2 专用事件幂等表（D5）。新库和 pre-v40 库需分别核对迁移范围。

## 5. 阶段 D：单笔与批量数据事务（D02—D05、D07、D03）

### D1. 打卡先写明细再提交档案

`checkin.rs::record_checkin` 改 `let mut conn = ...; let tx = conn.transaction()?`，明细 upsert **用 `?` 传播错误**，保持现有 `ON CONFLICT ... WHERE created_at != excluded.created_at` 的重复日期口径。在同一事务里从明细倒推连续天数／累计天数、更新 profile，并**在提交前于事务内回读真实档案**；只有读值和 `tx.commit()` 都成功才把已取得的结果返回给 `lib.rs`，允许 emit `checkin-recorded`、生成气泡或 TTS。不要先 commit 再做可能失败的回读并把“实际已提交”错误地报告为“未提交”。现有重算累计数的 `.unwrap_or(0)` 应改为传播数据库错误，防止读失败时将正确信息写成 0。为避免并发重复打卡误判，让“今天是否已打卡”判定与 upsert 在同一连接／事务内进行，并返回带 `already_checked_in` 的内部结果；不要在事务外先猜重复再决定文案。

**反测：**临时或内存库用 trigger 拒绝明细 INSERT，断言方法返回 Err，档案不新建／不更新，无“成功”气泡；重试成功后明细、连续、累计同时正确；当天第二条真实打卡保留既有重复文案。不碰真实用户名／数据库。

### D2. 批量补签遇一条失败就整体回滚

`checkin.rs::batch_checkin` 的 `query_map(...).flatten()` 改为遇行解析错误即返回；`tx.execute` 的两处 `let _ =` 改为 `?`，带 uid **脱敏或内部错误上下文**。`INSERT OR IGNORE` 返回受影响行数 0／1，`total_inserted` 只加真实插入数；profile 的 `UPDATE` 若应命中用户却受影响 0 行，按错误处理。**所有计数只在 `tx.commit()` 成功后**返回成功结果，失败让事务自动回滚并展示 GM 错误，不报“操作完成”。不要借此顺手改批量补签到“连续天数直接等于累计天数”的既有业务口径，另列算法决策。

**反测：**2 个虚构用户中一人的明细 INSERT 或档案 UPDATE trigger 失败，整批的明细／卡片／profile 不应部分生效，结果不得说已插入；`INSERT OR IGNORE` 因唯一键跳过时真实受影响数为 0。现有“成功计数”单测需同步。

### D3. 点赞事务一次提交，标记与加卡共同成败

`checkin.rs::add_likes` 在同一 `IMMEDIATE` SQLite 事务里完成**本日点赞累加→连续天数／第7天奖卡及标记→自然周30赞判定、周标记及卡数**，任一 SQL 或 commit 失败回滚整个事件，从而保证不再“卡已发、领取标记未保存”。**这是比旧版更强的整事件原子策略，不是无损迁移：**迁移前先持久化当日点赞，再分别处理周奖／连赞奖；若新版在卡片更新错误时连点赞也回滚、且服务端没有重投，就会丢这次合法点赞。实施前必须让用户确认：接受整事件回滚并配套持久化失败事件／可重试补偿（不能只依赖服务端重投），还是采用“点赞先提交，奖励失败另建待处理账本”保证赞不丢。无论哪种策略，卡数与其对应领取标记必须同一事务；**未确认失败策略前不得上线 D3**。改掉关键查询的 `.ok()`／`unwrap_or(0)` 把 SQL 错误伪造成“无行”的做法：只有 `QueryReturnedNoRows` 返回默认 0，其他错误必须传播。数值阈值和文案顺序仍与旧版一致：**返回时先“今日满30”后“连续7天”**，仅成功提交后 emit 奖励事件／入 TTS 队列。`handle_incoming_like` 第1091—1093行不再静默吞错，至少记脱敏 ERROR。

还有一个联动：当前 `handle_incoming_like` **在 SQL 前**把 `msg_id` 写入内存 LRU；若数据库失败，同一事件重投会被缓存拦截。修改 `src-tauri/src/bilibili.rs::MsgIdCache` 和 `DanmuProcessor::is_duplicate_msg_id` 的使用方式，让点赞专用调用支持“处理中保留／提交后确认／失败撤销”三态，并让并发同 ID 只能一条进入 DB；**现有 DM 点怪仍通过同一缓存**，需保持“先成功占用 ID 再处理一次”的行为和共享缓存语义，不能在 DM 分支与点赞分支重复登记同一个首次 ID。空 `msg_id` 不得假造唯一键阻止合法多次点赞。若未来要求跨重启的点赞幂等，再扩展 SQLite 业务事件表，不能把本轮内存缓存称为永久去重。

**反测：**在 streak 标记 UPSERT、每日点赞、周奖卡更新三个位置分别注入失败；第7天重复两次也不能多发卡，失败后内存去重保留应释放并允许重试；成功同 `msg_id` 只统计一次，DM 与 LIKE 共用缓存时交错也不能重复消费或误杀首次 DM；第7天＋当日满30 可按旧规则领两张且两条回复顺序正确；跨周、周一与跨年边界复测。全部在独立内存／临时库运行。

### D4. 三条合法补签不得被学习器吞掉

在 `lib.rs::handle_incoming_danmu` 第816—969行只让 `CheckinLearner::should_skip_duplicate` 控制 **CaptainCheckInModule 对打卡的**重复防刷屏；补签操作和补签查询的路由不受其返回值影响，仍按 `guard_level > 0 || has_medal` 判权限。打卡总开关关闭时补签仍独立可用。别把所有相同内容无条件放行打卡；也不要通过“修改第3条计数阈值”掩盖模块边界错误。

**反测：**构造用户至少 3 张卡、3 个缺日，连续发 3 个不同 `msg_id` 的“补签”，三个缺日均被处理并各回一条补签结果；第3条不能退化成普通弹幕朗读。重复“打卡”仍遵循旧模块防刷屏。完整形态用真实生产构造的 learner 走该管道；Lite 三条指令均不写库。

### D5. 无行≠SQL 故障；修复继承的同 `msg_id` 双扣

`checkin.rs::load_cards`、连续赞／每日赞读取改为**可区别 `QueryReturnedNoRows` 与其他 SQLite 错误的 `Result`**。无卡行视 0 张；查询三表皆无行显示“补签卡0张／连续点赞7天：已0天，差7天／每周点赞30：0/30，差30”；真正 SQL 错才记录故障并返回“系统错误”。同步更新 `checkin.rs` 第1873—1877、1908—1911行反向旧单测；不要再依据早期迁移文档的误写结论。

旧问题 I01 本方案一并修复：在 V2 初始化事务创建专用去重表（例如带 `uid,msg_id` 唯一键的 `processed_retro_commands`；先核对服务端 `msg_id` 的跨用户／跨会话语义，若不保证全局唯一则额外引入稳定会话命名空间）。**仅对非空 `msg_id` 且真正要扣卡补签的路径**，在同一 SQLite 事务中插唯一键、扣卡、插缺日明细、重算档案，整个 commit 成功后才算“已处理”。相同已提交 ID 重投返回 `Duplicate`，不再扣卡／重复播报；SQL 失败回滚去重占位，让重投可重试。无卡、满勤、无缺日等只读反馈**不写入幂等键**，再次重投仍能按当前资产给出正常提示；纯补签查询也不写键。`retro_command_outcome` 当前“先释放 conn 锁、再逐步加锁”的实现必须改为持同一 `Transaction` 的内部查缺日助手，避免在命令拆分之间选中同一天；扣卡 SQL 应包含 `card_count>0` 并核对受影响行为 1，profile 更新也需核对命中 1 行。无 `msg_id` 不要用消息文字＋时间伪造键，否则会把合法多次补签一并挡掉；记录脱敏 WARN 即可。旧库添加一张 **V2 专用表**，不得改旧五张业务表的列语义；当前 `checkin.rs::test_open_legacy_captain_profiles_db` 第1520—1534行、`test_v2_schema_matches_legacy_format` 第1544—1574行、`test_real_repo_legacy_db_copy_compatible` 附近、`test_publish_db_schema_migration_on_real_legacy` 第2304—2315行等所有“表总数不变”断言都要更新为：“允许旧 `cumulative_days`／`weekly_first_claimed` 必要缺列迁移＋仅新增一张声明的 V2 幂等表；原五张表的非目标列与历史行不得改变”。分别用 v40+ 新库、pre-v40 合成旧库及**授权的隔离旧库快照**测试幂等，不能只更新一条测试让另两条假失败。若实施中发现产品禁止在旧库添加 V2 表，应先暂停该项、明确申请取舍并同步调整发布门禁；不能暗中退回内存去重却声称重启后完全幂等。

**反测：**同 `msg_id` 重投两次只能扣一张且同一次补签只写一条；不同 `msg_id` 连续补多个缺日不受影响；第二条与第一条并发也只能一张；数据库失败回滚去重记录后可重试。空 `msg_id` 保持旧语义。Lite 不创建去重表、不运行补签。

## 6. 阶段 E：凭据一致性和直播会话生命周期（K01、L02、L03）

### E1. 可信凭据快照，不让配置页覆写密钥

`lib.rs::AppState` 的 `credentials: Arc<Credentials>` 改为所有 AppState 克隆共享的可变**凭据快照**（如 `Arc<RwLock<CredentialState>>`，内含验签后值与 `loaded`）。连接 `set_bili_connection`、`get_credentials_status`、`save_app_config`、`apply_credentials_live` 统一从同一次快照读，不能一部分读旧 `Arc`、另一部分读 `config` 镜像。前端 `newCfg` 的敏感字段一律忽略，应用凭据由已验签文件独占，`IdCode` 仍独立注册表；Manbo Key 仍独立注册表，不从凭据里的 `special_user_tts_api_key` 反写。

文件导入必须**先**校验格式／签名和必要字段、预构造 B 的所有内存快照与 TTS／AI 所需配置，再在规范目录的唯一临时文件写完并同步，安全替换 `credentials.dat`；替换失败则旧文件、旧内存仍可用。Rust `fs::rename` 对目标普通文件已存在时可尝试替换，不能按“Windows 必败”处理；权限／占用仍需错误处理。**磁盘 B 已提交、内存 B 发布失败时不得返回导入成功：**优先在同一短提交闸门下重新读回并验签磁盘 B 后更新唯一权威快照；若仍不可用，进入禁止开播且高可见的凭据错误状态，保留错误供人工恢复；只有能验证旧文件备份和回滚结果时才允许恢复 A。AI／TTS 更新失败须告警并在修复后基于 B 重试，不能让凭据状态报告 B、引擎却静默使用 A。完整成功后同一个写锁内发布凭据快照并同步配置／AI／TTS；密钥不回显到 Logs、前端配置 JSON、异常信息。采用虚构的 A／B 测试凭据，不碰真实文件。

### E2. 导入“即时生效”的准确界线

运行中的 `run_bili_live_loop` 以值持有旧 `BiliCredentials`，换内存锁**不会**让现有 WebSocket 自动改用 B。确定的最小政策是：**Connecting／Connected／Reconnecting 或旧连接任务尚未退出时拒绝导入，任何磁盘复制前即返回“请先断开连接”；成功导入在当前进程下一次连接无需重启即可用 B。** UI 文案明确该语义，不写“现有连接已切换”。如果文件选择仍用 `blocking_pick_file()`，必须在取得任何保存／生命周期锁**之前**完成，不能持锁等待用户点对话框。

会话 start／stop／import 必须共用**同一个** Tokio 异步生命周期闸门（由 async 命令持有），保证 `set_bili_connection(true)` 的“检查空闲→取得凭据快照→登记新会话／启动任务”与 `import_credentials_file` 的“检查旧任务已退出且服务端关闭已确认→替换文件→发布 B”互斥；不能只分别读 `is_running` 与凭据 RwLock，再在空隙里启动 A。同步的 `save_app_config` 不得在运行时线程上 `blocking_lock()` 该 Tokio 锁。另用短时 `std::sync::Mutex` 串行配置保存与导入的“文件原子替换→发布内存凭据→同步 AI／TTS”，只在**不含 `.await`** 的提交区持有。建议固定锁序“异步 lifecycle → 同步 credential_gate → credentials RwLock → config Mutex”；克隆所需配置后先释放子锁再进入 AI／TTS 的内部锁，避免反向获取。

要让“先断开”可靠，`BiliLiveService` 必须管理当前连接任务的取消、退出确认和会话结束状态（如任务句柄／会话 generation）；断开调用者等待旧任务结束或明确返回“正在断开”，不得只把 `running=false` 后立刻允许新 `true` 复活旧循环。退避 `sleep` 和 WS select 应支持取消；**不能跨 `.await` 持 `std::sync::Mutex`**。停止旧会话需要用旧 A 下播。**仅当服务端明确确认 end 成功且旧循环已退出时**，才允许导入 B／开始新会话；end 网络超时／失败时保留可重试的 game_id 和“服务器关闭状态未知”标记，暂不按正常断开放行轮换或自动重开。旧会话失效／无法再 end 的恢复规则需产品确认，不能把超时默认当成功。若另需“连接中自动热切 B”，必须设计完整 stop-and-join(A)→换文件和内存(B)→start(B) 的事务式流程并征得产品选择，本轮不假装仅换 `Arc` 即可实现。

**反测：**启动 A→断开且等旧任务退出、**确认 end 成功**→导入 B→不重启连接，构造的 start 请求使用 B；`get_credentials_status` 立刻报告 B，2.5 秒后不会跳回 A；第一次从空导入 B 状态为 loaded；导入中途文件写失败旧 A 仍有效；文件已替换成 B 后模拟内存发布／AI／TTS 更新失败，不能返回“导入成功”，状态需准确标明暂禁开播／待补偿，恢复前不能混用 A/B；活跃会话尝试导入 B 时旧文件和状态零变化。用两个受控线程屏障让“准备启动 A”与“开始导入 B”同时到达生命周期闸门：最终要么先注册活动 A 并拒绝 B，要么先提交 B 且新连接只读 B，不能出现会话 A 同时磁盘／内存为 B。旧会话 end 超时／HTTP 500 后仍持有可重试 game_id 与“关闭状态未知”，不能允许 B 轮换或直接再开；断开发生在 start 请求途中时，start 返回 game_id 也必须先用 A 正确下播。只使用本机假 API／假凭据，禁止触发真实平台。

### E3. 心跳解析与下播成功不再伪造

`bilibili.rs::heartbeat_app` 将响应 `code` 提取到可单测纯函数：不存在、非整数、`i32::try_from` 越界均返回无效响应错误，不能 `unwrap_or(0) as i32`。成功只按现有协议允许 `0/4004`；错误经现有 `HeartbeatTimeout`／网络失败状态机处理，日志只记错误类型与非敏感状态，不回显响应原文。

`BiliCredentials::end_app` 不得忽略 `.send()`：网络错误／非 2xx／JSON 无有效成功码返回 Err，只有明确证实关闭成功才 INFO。先理顺 `set_bili_connection(false)` 与后台 `running=false` **双 end**：给每个会话显式结束状态 `active/ending/confirmed/unknown`，持短锁把活动 game_id 标记为 `ending` 取得该次 end 的唯一执行权，**不要先 `take()` 丢掉唯一可重试 ID**；后台看到已经在 `ending` 时不重复 end。若停止时 start_app 尚在路上，收到新 game_id 后由后台独占 end 并等待确认。成功后才清理 ID、释放新会话许可；失败／超时转 `unknown`、保留 ID 和原凭据快照供受控重试／状态查询，禁止把“本地已停止”写成“服务端已关闭”。重连前失败也 WARN、按已确认的业务退避规则处理，不能谎称“已关闭”，更不能无条件继续新 start 命中 7001。`shutdown_app` 不阻塞网络是现有显式取舍：退出时可记录“服务端关闭状态未知”，但不可借此允许**同进程**在未确认下立即开新会话。

**反测：**无外网的可注入 fake transport／本地 loopback 返回 `code=0/4004/7001`、`{}`、字符串、`4294967296`，验证重连与日志；主动断开、start 进行中断开、断网重连，各 game_id 只下播一次；非成功响应不输出假阳性 INFO。

## 7. 阶段 F：History 和诊断日志各归其位（L01、L04—L06）

### F1. 完整版从业务事件写 History，不从 TTS 出队写

当前 `lib.rs` 第2048—2051行在播报泵统一调用 `record_history`，需删除此唯一入口后按**实际业务文本形成的时间**分配留档：

| 来源／入口 | 完整版 History 要记录什么、何时记录 | Lite |
|---|---|---|
| 正常 DM（含点怪、打卡／补签指令、被语音过滤的弹幕） | 有效原始 DM 一进站、在打卡与点怪去重／过滤前写一次 `"{uname} 说：{msg}"`；旧版仅当粉丝牌佩戴字段、舰长等级、昵称、消息等必需字段齐全才入独立 History 队列。`bilibili.rs::parse_danmu_json` 当前用默认值拼 `DanmuData`，需返回／随载荷携带 `has_history_required_fields`，让真实 WS 调用与模拟事件两条管道都按同一判定留档；不得把畸形空值 DM 写成“ 说：”。同 `msg_id` 重投是否两条，先维持旧原始 DM 留档口径。 | 不记 DM History，仍正常点怪 |
| 首次／重复打卡 | AI／兜底文案最终确定时，在 emit／TTS 前记回复一次；无语音也记。原 DM 已另记一次。 | 不记 |
| 补签与补签查询 | `retro_command_outcome`／`query_reply` 算出真实回复后各记一次；查询原样保留包含换行的三行文案，虽物理文件多行但只调用一次 `record_history`。 | 不记 |
| 点赞奖卡 | 事务提交后，对实际发出的每条奖励回复记一次；普通点赞无回复不记。 | 不记 |
| SC／上舰／进场 | 通过 `tts_text()` 得到合法 SC／Guard 文案后、判断语音开关前记一次；`RoomEnter` 当前已记一次，保留。 | 不记 |
| 礼物连击 | 原事件经过 `GiftComboTracker::handle` 形成首报／即时报告时记；`tick` 超时形成**合并结算文案**时记，不能对每个原始礼物另记。即使关闭语音也要推进 tracker；“仅付费播报”过滤与 History 分开，必要时让 tracker 返回 `{text,can_speak}` 而非在内部丢弃免费历史。 | 不记 |

队满、合成失败、语音总开关关、粉丝牌播报门槛均不能回头删除业务 History。点餐原 DM 留档即可，**不因多生成一个接单 TTS 文案再多记一条**。`logging::record_history` 当前在 `cfg(test)` 下完全不落盘；测试需注入只在测试使用的收集器或独立临时目录 sink，断言**业务调用链**，不能只断言行格式。真实 WS 解析与本地模拟各用“合法必需字段齐全／缺佩戴状态或等级／缺昵称或 msg”表格验一遍；完整版合法且关语音各留原文一次，缺字段不生成虚假 History；Lite 仍不留。旧完整版 `TextToSpeech::Tick` 是独立队列延后写盘；改到接收路径会增加同步 I/O，发布前须依第 9 节测量。若有瓶颈，再加**有界单写者队列与丢弃可见告警**，不加无界 spawn。History 与诊断 Logs 权限和隐私用途不同，不能把用户原文复制到 INFO。

### F2. 缺资源告警有冷启动快照

setup 中 `ensure_seeded()` 后计算一次缺失资源集合，存入 AppState（如 `startup_missing`），新增只读 `get_missing_resources` IPC；已有 WARN 和 `resource-missing` 事件继续保留。前端先订阅事件，再读快照，按资源名去重并合并 Toast；晚于 setup 注册也能读到全部缺项。**Lite 仅把核心点怪必需资源视为告警**，不能因为停用语音／分词素材缺失就显示其业务失败。隔离目录测试“事件先于 listener”和“listener 先于事件”两种时序，不删除真实资源、不运行旧包。

### F3. 正常状态可观测，诊断 Logs 不泄漏业务原文

诊断 Logs 的脱敏是**全量改造而不只是新日志**：逐项审计所有 `log_info!/log_warn!/log_error!` 调用及由 reqwest／TTS 错误间接带入的字符串。当前须至少处理：`lib.rs` 第985—989、1013—1019行正常点怪与禁点拦截的昵称，第361、367、387、392行用户可编辑怪名，第745、900、1558行外部错误／导入路径，`tts.rs` 第831—837行队满时的原文前 20 字，`bilibili.rs` 第461—473行点赞 JSON／UID、第1164—1173行 game_id、第1184—1195、1275行服务端错误、第1364、1401行游戏 ID／WSS URL 及接收错误。对业务量只记数量／失败类别和自动生成的匿名追踪 ID；对路径只在本机受控诊断入口显示，不进普通 INFO；外部 HTTP 错误仅记状态码和固定分类，不能直接输出服务端响应全文。`lib.rs::apply_connection_status` 只在状态或 reason／attempt 实际变化时记安全 INFO：旧状态→新状态、失败类别、重试次数。`bilibili.rs` 正常 WebSocket 收包必须维护**固定白名单 cmd 类型计数**并周期性输出有上限的 INFO 摘要（包括收到 DM 但未点怪的情况）；无法识别的 cmd 固定标为“other”。不能每条直播包都打文件：在完整 60 秒观察窗口里固定每个类型至多一条统计摘要，性能门禁验证长期业务负荷。Lite 仍记连接与 DM 类型的健康统计。所有允许的日志字段做单行 CR／LF 转义，防伪造新的 `[ERROR]` 行。History 保持用户业务文本原样及查询多行，不强行转义以致破坏旧留档。

日志入内存环与文件由**同一个串行临界区**决定顺序，或至少分配单调序号并有序写入；不可一个锁先入环、另一个锁稍后写盘导致复盘先后相反。`clear_recent` 仅清内存，读写锁序不要倒置；文件写失败仍要让内存记录可见，不递归调用本身的 `log`。现有 LF 行尾与旧 Windows CRT 的 CRLF 不逐字相同；**默认保持 LF**，只有出现明确的按字节消费需求才一起更新日志、History 与回归断言。现有主界面没有日志页，不额外承诺加 UI。

**反测：**两线程屏障令 A 内存入环后暂停、B 尝试写文件，最终环／文件同序；BOM 只出现一次，内存环仍限 500 条。用固定虚构 secret、昵称、怪名、URL、uid 和含 CR/LF 的文本分别驱动正常点怪成功／禁点、字典编辑、点赞缺字段、TTS 队满、凭据导入、B 站错误路径；对**内存环和 Logs 文件全文**断言均不含敏感标记、原始业务正文及伪造的 `[ERROR]` 行。这个测试必须覆盖已有日志调用点，而非只测新增的连接状态 INFO。`logging.rs` 的崩溃报告测试第485—490行写失败会静默“通过”，应将输出路径改为测试可注入并**断言**临时目录确实写成功。

## 8. 待确认、不自动擅改的产品行为与旧问题

1. **人工拖拽的顺位生命周期：**当前新点怪触发 `QueueManager::sort_queue`，可能恢复时间排序并覆盖手排结果。若要“手排直至主播下次调整”，需要专门持久化人工顺位标记并定义新单插入位置；若要“新点怪恢复算法排序”，只修 Q01 的丢单、不扩展排序算法。须先由产品确认。
2. **悬浮窗整行点击完成：**旧工程也可单击完成，但历史记录写用户确认过显式“完成”按钮；当前悬浮窗整行可点击且可 5.2s 内撤销。确认是否以新 UI 需求覆盖历史决定；若要按钮，限定删除入口为按钮、保留拖拽手柄，补误点用例。
3. **气泡与真正播放时间：**V2 emit 立即出气泡且 15 秒过期，积压 TTS 后可能先消失。若要求旧版“声音开始时显示”，只移动 emit 到 `speak_task` **不够**：`AudioQueue` 还有串行 mpsc 等待。应由音频 Job 真的开始（SAPI 子进程已启动／rodio sink 已 append）发一次播放开始事件，失败回退立即显示；若坚持即时气泡，把它声明为产品差异并在队列积压测试中验收。Lite 无气泡。
4. **继承问题 I01：**相同 `msg_id` 弹幕重投可能重复扣卡，D5 给出完整幂等方案。周奖卡遇旧周迟到赞可能倒退领取标记、旧日期到达可回写 last date，迁移前同样存在；没有真实乱序证据，不能伪称本轮已修。若决定加强过期事件校验，必须先定义接收延迟、补录和手动测试的业务上限。

## 9. 实施顺序、测试矩阵与发布门禁

建议顺序：**A1+A2（守住单）→ C1+C2（禁止资产假持久）→ D1+D2+D3+D4+D5（数据事务、三连补签与补签幂等）→ B1+B2+B3+B4（词库与名单）→ E1/E2/E3（轮换及网络）→ F1/F2/F3（历史及诊断）→ 第 8 节其余产品决策**。D5 的持久化去重需明确核准增加一张 V2 专用表；若产品不同意，暂停该项并修订门禁，不悄悄降级。每一批次先运行**该批次已实施范围**的反向测试和现有回归；只有进入最终发布门禁时才要求 A—F（含 D5）的全部测试同时通过。若新增 V2 去重表需额外用户确认而 D5 暂停，不能把 I01 测试列为已经通过或称本方案全部完成，须单独记录发布阻塞／已知风险并请用户重新定范围。若早期批次调整了 IPC 快照类型，两个前端及 Rust 事件一次性同步，不能在半套协议状态发布。

| Rust 完整版：`cargo test --manifest-path src-tauri/Cargo.toml` | Queue revision、刷盘可控屏障、字典同名、名单 API 多线程、D01/D02/D04/D05 的 SQL 故障 trigger、D03 三次不同 msg_id 补签、I01 同 msg_id 幂等及无行文案，`[PASS]` 标记 | 测试私有 temp 目录／纯内存 SQLite；不用真实库 |

**性能数据采集方法（尚无结果）：**在隔离生产构建上用固定 175 条怪物词库，回放相同的 500／5000 条合成 DM，至少三次记录入口处理 p50/p95/p99、queue mutex 等待、每 500ms 磁盘写入次数与最长用时，以及启用／关闭 History 时的 WS 接收延迟；同时在单盘 I/O 故障、名单慢盘写入下观察排队延迟。记录 Windows 版本、CPU、盘型、构建模式与历史任务数。只有采样后才能决定 History 需不需要有界单写者队列，不能先声称锁外写盘或同步留档“性能更快”。

**明确不承诺的范围：**进程内版本／写锁不能协调两个独立进程同时指向同一配置目录；Windows 目标文件被外部独占打开时重命名仍可能失败；`sync_all+rename` 不等于任意断电必不丢；AI／TTS 外部服务质量需独立人工验收。上述情况必须在发布说明中如实写出，而不是用缺乏实测的“完全兼容”代替。
